# Public vulnerability evidence and firmware 14.10

Reviewed 20 October 2026. This ledger records **disclosures and source claims**, not executable validation. No payload, proof of concept, or console test was run. A vendor advisory for FreeBSD or Apple does not establish that the same code and patch state exist in PS5 system software.

## Firmware-specific baseline

[Sony's 26.06-14.10.00 release notes](https://www.playstation.com/en-gb/support/hardware/ps5/system-software-info/) state that the release contains security fixes. Sony does not name a CVE, component, or before/after patch state there. The existing [offline package analysis](analysis-14.10.md) measures an outer update wrapper; it cannot identify installed WebKit or kernel code. **No issue in the table below has verified 14.10 applicability.** Likewise, absence from an older project's supported-version list is not proof that a particular vulnerability was patched in 14.10.

## Security boundaries and evidence gaps

The public projects distinguish a browser entry, a kernel vulnerability, and later privilege or payload stages. A CVE affecting one component cannot establish the prerequisites or mitigation state of the others. In particular, the UMTX project's own account says its later firmware work needs a separate browser entry. Its descriptions of hypervisor, CFI, XOM, SMEP and SMAP are historical project observations; they are **not measurements of 14.10**.

Useful non-exploit verification work is limited to:

1. Obtain a Sony-published, version-bound component or security bulletin for 14.10, if one exists, and map any named CVE to the stated firmware range. Record the exact URL and retrieval date.
2. Compare documentation and legally available source disclosures for component versions and mitigation statements. Mark inferred PS5 applicability as unresolved until an authoritative Sony source or independently reviewable version evidence exists.
3. Maintain a firmware support matrix derived from pinned project code and README files, with separate columns for an author's claimed affected range, the tested/integrated range, and an actual code gate. A synthetic static check of the gate can confirm that `14.10` is absent without executing it on a console.
4. Track whether future release notes name specific fixes. A generic statement that 14.10 contains security fixes cannot identify which historical CVE, if any, was addressed.

No row supports a jailbreak claim for 14.10. The outstanding question is the **actual 14.10 component and patch state**, followed by independent evidence for each prerequisite security boundary. Offline wrapper statistics cannot answer either question.

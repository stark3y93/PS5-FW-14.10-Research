For each historical V429/V432/V445 claim, locate the original complete beacon session, timestamps, console model, and test source revision. 2. **Establish firmware provenance.** Record the PUP SHA-256 with `--sha256`; compare its official package identifier/version through trusted Sony metadata. The `SLB2` header alone cannot identify WebKit or kernel patch state. Analyze only legally available, readable components; do not infer contents from encrypted payload sizes.

This is the strongest browser direction because a vendor-confirmed UAF and regression test exist upstream. A source match would establish candidacy, not exploitation.

Do not infer a 4.29 GB PS5 write from a successful compile or a lost beacon. The corrected V480 negative control must accompany any interpretation of prior p146/p148 logs.
5. **Audit FreeBSD candidates against the Sony fork.** Compare the exact patched functions for CVE-2026-7270 and CVE-2026-45251 with any authorized 14.10 kernel artifact, then separately assess syscall accessibility from the relevant sandbox. Without both, leave them as upstream-only candidates.
6. **Document chain gaps.** A browser process weakness still needs a reliable memory primitive, sandbox crossing, kernel primitive, and (for certain protected operations) an additional hypervisor or content-protection bypass. Record each stage separately; Debug Settings alone does not validate later stages.

These steps are read-only. No live payloads, console changes, or dependency installation are required.
